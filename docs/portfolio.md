# Vaultix · Материал для портфолио

**Задача.** Показать, как внутренний банковский перевод сохраняет целостность при повторе HTTP-запроса, параллельных списаниях и отказе внутри транзакции.

**Мой вклад.** Я сформулировал задачу и критерии приёмки, определил объём учебного стенда и требования к воспроизводимым проверкам. Аналитические артефакты и приложение подготовлены с помощью Codex.

**Требования.** Клиент владеет источником, счета активны, сумма в копейках укладывается в остаток и лимиты. Перевод создаёт ровно две равные встречные записи, а повтор сохраняет исходный результат.

**Архитектура.** Модульный монолит на FastAPI и React с PostgreSQL. Остатки по журналу, детерминированный порядок блокировок, транзакционные записи результата ключа и аудита. Лаборатория работает с отдельной базой и тем же HTTP-обработчиком.

**Реализация.** Кабинет клиента, рабочее место оператора, управление пользователями и лимитами, аудит и восемь сценариев лаборатории. Требования связаны с правилами, контрактом, кодом и проверками.

**Проверка.** Для конкурентного списания API возвращает HTTP 201 и 409. Сравнение снимков показывает один перевод. При сбое журнал и остатки совпадают со снимком до запроса. Подробности в [отчёте](testing/results.md).

**Результат.** Репозиторий содержит запускаемый стенд, двуязычное описание, OpenAPI, архитектурные решения и реальные скриншоты.

**Демонстрация на интервью.** Начните с BR-008 и UC-01, откройте sequence diagram, запустите два конкурентных списания и сопоставьте ответы с проводками. Затем покажите откат и поясните, почему после серверной ошибки тот же ключ допускает повтор, а изменённое тело сохранённого запроса даёт конфликт.
